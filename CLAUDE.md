# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

zboe2 (Zombie Biohazard Outbreak Experiment 2) is a web-based multiplayer zombie-hunting game — a NodeJS/Express rewrite of an older IRC-based game. Early development (this is the first playable dev-rc after a prior build was lost to a drive failure). Pure ESM (`"type": "module"`), no build step, no test suite, no linter configured. Long-term direction: a text-based zombie-themed RPG with a traversal map of named locations (some zombie-threatened, some safe), a dynamic per-location actions panel, crafting/smithing, armor, spells, and resource gathering — several currently-idle hooks (e.g. `getLocationCount`, `public/img/` for location/state backgrounds) exist for that.

## Commands

```bash
npm run dev       # node server.js --dev --debug=FULL
npm run stable    # node server.js
npm run verbose   # node server.js --verbose
node util/index.mjs [group action args...]   # Admin CLI: REPL with no args, one-shot with args
```

Server listens on `PORT` (default 3000), over **HTTPS when `ssl_config.enabled`** (PEM `certFile`/`keyFile`, relative paths resolve from the project root; all cookies flip to `Secure` automatically; enabled-but-unreadable certs are a FATAL — no silent HTTP fallback, and the daemonizer pre-validates them before forking so the child can't die silently). The server manages its own foreground/background lifecycle (see `--verbose` / `--stop` below) — there is no systemd unit, and the Docker files were removed (they predated the self-backgrounding and never worked with it). The (gitignored) `install-*.sh` scripts install Node + npm deps, point at this lifecycle, and — if they detect nginx or Apache on the machine — print a ready-to-paste reverse-proxy snippet; the full proxy/HTTPS walkthrough is **`INSTALL.md`** (tracked). `./zboe.sh` is a `dialog` TUI: the Server menu starts/stops/restarts via `node server.js` / `node server.js --stop` (reading `logs/zboe.pid`), plus User/Player/Database/Log admin menus and the Admin CLI.

**Runtime flags** (parsed by a declarative `CLI_OPTIONS` table in `server.js`):
- `--dev` / `--production` (mutually exclusive).
- `-v` / `--verbose` — **foreground/background switch.** With it, the process stays attached as a live, colorized console. Without it, the process re-spawns itself detached, prints a couple of lines + the child PID, writes `logs/zboe.pid`, and releases the terminal.
- `--stop` — SIGTERMs the backgrounded server via `logs/zboe.pid` (handles missing/stale PID files).
- `--debug-level=<FULL|INFO|WARN|ERROR|FATAL>` and its alias `--debug=<LEVEL>` (the alias is real now — the old `--debug=` vs `--debug-level=` discrepancy is fixed).
- `--set group.key=value` (repeatable), `--group.key=value`, or bare `--key=value` — override any value in `file_config`/`game_config`/`zombie_config` for a single run, type-coerced to the existing value's type. Overrides are in-memory only; they don't write back to `config.js`.
- `--mock-db` — seeds a starter dev DB (`admin` + `player1` + `player2`, one admin) with random 5-char passwords, printed **to the console only** (never the log file). Idempotent — skips existing users.
- `-h` / `--help`.

## Architecture

Three layers, with `db.js` as the hard boundary between the web layer and SQLite — plus `item_backbone.js`, a pure-data item/recipe registry at the bottom of the stack that both db.js and server.js import.

**`db.js` — the only place SQL lives, and the source of truth for game rules.** On import it opens/creates `data/zboe.sqlite` (WAL, foreign keys on), runs `CREATE TABLE IF NOT EXISTS` for the full schema, seeds the single `game_state` row (`key = 'main'`), and does a couple of legacy `ALTER TABLE` column-adds. It defines prepared statements once and exports thin named accessors. **Nothing outside `db.js` writes raw SQL** — the one exception is `util/commands/*.mjs`, which imports the raw `db` handle for admin ops. Add game state as a column/table + a matching exported accessor here, not as a query in `server.js`. Beyond accessors it also owns/exports: `GUN_TYPES`/`GUN_NAMES`, `DB_PATH`, the world (`LOCATION_NAMES` — its keys are the canonical location list — `LOCATION_LINKS`, `ZOMBIE_LOCATIONS`, `LOCATION_ACTIONS`), the skills (`SKILLS`/`SKILL_NAMES`/`skillLevelCost`/`addSkillXp`/`spendSkillLevel`), the **`EDITABLE_STATS`** whitelist + `setPlayerStat` (used by both the CLI and the web admin), and the **leveling rules** (`nextLevelOf`/`prevLevelOf`/`levelCost`, `LEVEL_*_BONUS`, `applyLevelUp`, `forceLevel`). Put shared game math here, not duplicated in `server.js` or the CLI.

Core tables:
- `users` — auth (`is_admin`, `pass_salt`/`pass_hash`, `last_login`).
- `players` — 1:1 stats. `xp` (spendable) + `lifetime_xp` (leaderboard rank) + `level`; `health`/`max_health`; `shield`/`max_shield` (shield caps at `max_shield`, not a fixed 100); `golden_shots` (Golden Gun power-up counter); `accuracy`, `kills`, `gold`, `horde_tokens`, `equipped_gun`, `location`, `hidden`, `last_seen`. **Ammo/clips/condition/jam are per gun type**: `handgun_*`, `rifle_*`, `shotgun_*` (`_ammo`, `_max_ammo`, `_clips`, `_max_clips`, `_condition`, `_jammed`) — there is no player-level `jammed` flag; a jammed Rifle doesn't stop the Handgun. Page stats read from whichever gun is equipped. **Skills are per-skill column pairs**: `s_<skill>_lvl`/`s_<skill>_xp` for magic/woodcutting/fishing/mining/smithing/crafting (`SKILLS`/`SKILL_NAMES` in db.js).
- `player_inventory` — items (guns are inventory items; a consumed consumable stays at qty 0, visible-but-unusable).
- `events` — global feed. `type` (spawn/kill/shoot/attack/death/chat/system/level/item/shop/reload/travel/action), `visibility` (public/private/background — `background` is hidden from the feed), and `target` (`'global'` or a stringified `user_id`; the feed query returns global + your own).
- `game_state` — one `key='main'` row: `hunt_enabled`, `horde_size`, `horde_status`, `raid_enabled`, `online_players`, `base_health`, `base_destroyed_at`.
- `nuke_votes` — ballots while the base is destroyed. (There is no items table — the item catalogue is code, see `item_backbone.js` below.)

**`server.js` — Express app, auth, game-state API, and the game tick.** Session auth is a hand-rolled signed cookie (`zboe_session`): base64url JSON + HMAC-SHA256 keyed on `game_config.sessionSecret`; passwords are PBKDF2-SHA256. **On top of that sits a server-side session pair** (anti-hijack): login/register mint a random 25-char key + UUID; the key is HMAC-salted with `sessionSecret` before storage (the DB never holds the raw value), written to *both* `users` and `players` (`session_key`/`session_id`, defaults = the logged-out state `'LOGGED_OUT'` + 64 zeros), and carried by the browser as `zboe_skey`/`zboe_sid` httpOnly cookies (sent automatically — no page code involved). `requireAuth` verifies cookie-vs-stored *and* users-vs-players agreement; any mismatch logs a **WARN** with the IP and bounces to login. Logout voids the pair (`LOGGED_OUT` + zeros); a login against a non-logged-out session is **blocked while that session is active** (`last_seen` within `timeout`) and silently replaces it when stale — rotation kills the old cookies. `resetPlayer` copies the pair back onto the fresh players row so dying doesn't end the session. `requireAuth` populates `req.user`/`req.userId`; `requireAdmin` (checks `users.is_admin`) gates admin-only routes (hunt toggle, base reset, and the whole `/api/admin/*` panel API). The main frontend is one static page (`public/game.html`) that polls `GET /api/game-state` every 3s and composes one JSON response (player stats, world/base status, leaderboard, filtered events, online list). The page splits events into two feeds: **"Your Activity"** (left sidebar) shows the player's own `PERSONAL_TYPES` events (shoot/reload/shop/item/level/travel/action); the middle **World Feed** shows everything else (spawns, kills, attacks — including base attacks — deaths, chat, system). The navbar shows `app_version` (sent in game-state) and a Logout button. **Inventory is its own modal** (not a shop tab): **Toolbag** (registry `toolbag` consumables with Use buttons, greyed at qty 0) and **Backpack**, which nests type sub-tabs with type-specific columns — Guns (live cond/ammo/clips from the player row via `/api/inventory`'s `guns` array, jam badge, Equip), Tools (tier badge), Consumables (non-toolbag food, qty + Use), Materials (crafting/trade/treasure, qty). Level Up/Max buttons live in the Player Info modal, not the main HUD; the HUD statcard stacks health (red) / shield (blue) / **XP (gold, progress toward `nextLevelCost`)** bars. The right sidebar's **Players card combines the XP leaderboard and online presence**: the rank badge is green (online) or grey (offline), usernames use the level-tier shimmer gradient (`.shiny-name`, shared with the HUD name), and online players outside the top list are appended unranked. There is also a **web admin panel** at `/admin` (`public/admin.html`, admin-gated) — backed by `/api/admin/*` endpoints. Tabs: **World** (default — live hunt/horde/base state with toggle-hunt, set-horde-size (`POST /api/admin/world/horde`, keeps the raid latch coherent), reset-experiment, and an online-player table with location + safe/zombie + busy/campfire badges from the in-memory maps, via `GET /api/admin/world`); **Users** (CRUD); **Players** (a full player list — level/location/online, enriched via `listUsers`'s players join — that swaps to the Edit Player view on click; a **Player Card** mirroring the game HUD (level circle + health/shield/XP bars) with quick-edit rows beneath it for health/max/shield/max/gold/tokens (±/set plus **Refill** on health & shield = set to the matching max) — those six fields are excluded from the stats table, which stays grouped Core/per-gun/Skills with prefixes stripped; `forceLevel` control, a location teleport dropdown (`POST /api/admin/player/location` — bypasses the travel graph), gun equip, and inventory grants via a registry-driven dropdown); **Items** (read-only registry/recipes/static upgrades). The pre-login landing page (`public/index.html`) shows a live leaderboard from **`GET /api/leaderboard`, the one unauthenticated API endpoint** (rows: `{user, xp: lifetime_xp, level}`).

- **Game tick** (`startZombieTicker`, every `zombie_config.z_tic` s): spawns (`z_chance%`, **doubled during a raid**) then runs an attack tier — **wandering** (<`z_horde`: one zombie @ `z_hit%`), **hunting** (≥`z_horde`: up to 75% of zombies hit every active player), **raiding** (≥`z_raid`: each zombie @ `z_hit/2%` hits up to 10 players for double damage). Damage is shield-first then health (`damagePlayer`). Inside players are absorbed by the base (2 base HP each, up to 500); every surviving base hit emits a public world event (`The base was attacked for N (X/max HP)`); base death resets everyone inside; an outside player at 0 HP dies. Death = full reset to level 1 (`resetPlayer`). A destroyed base freezes the world until an admin reset, a passed nuke vote, or `experimentResetHours` elapse — then `experimentReset` wipes global state.
- **Raid is a latch, not a threshold.** Once the horde reaches `z_raid` it latches `raid_enabled` on (`latchRaidIfNeeded()`, called after every zombie add — tick spawn & call-zombie) and stays raiding until the horde is fully **cleared to 0** (handled in the shoot handler), regardless of dropping back below `z_raid`. `hordeStatusOf()` reads the latch first.
- **Tokens (`horde_tokens`):** the shooter who lands the horde-breaking kill (crossing below `z_horde`, non-raid) earns **+1**; the kill that clears the last zombie during a raid earns **+3**. Raid supersedes horde (no double award).
- **Leveling** (`/api/level/up`, `/api/level/max`): levels are strictly numerical (always +1); cost compounds (`levelCost = round(100 × level^1.6)`). **Stat bonuses (+5 accuracy capped at 100, +5 max health, heal to new max) apply on every level through 15, then only every 5th level (20, 25, …)** — `levelGrantsBonus()` in `db.js` decides; `applyLevelUp` returns a `bonus` flag the level-up message uses. `lifetime_xp` (the leaderboard rank) is untouched by spending. Admin `forceLevel` applies/reverses the same conditional bonuses without an XP cost. Rules live in `db.js`.
- **Presence:** `last_seen` is touched **only** by the game-state poll (the page's active refresh) and at login — actions no longer touch it. `online` = `getActivePlayers` within `game_config.timeout` seconds; drop by lowering `timeout`.
- **Shop = two sources, both code-defined.** Registry items with a `shop: {cost, currency}` block in `item_backbone.js` (`/api/shop`, `/api/shop/buy` by ITEMS key — currently the tools; `purchaseItem` in db.js is the transaction) plus the hardcoded `STATIC_UPGRADES` list in server.js (`/api/shop/upgrades`, `/api/shop/upgrades/buy` by `key`). Each static entry has a `category` (`"upgrade"` → Upgrades tab; `"item"` → Shop tab alongside registry items) and a `currency` (`"gold"` or `"token"`). The Shop tab has Backpack-style category sub-tabs — Consumables / Guns / Tools / Tokens — derived client-side (`shopCatOf`: token currency → Tokens, then by type). Covers stat boosts (equipped-gun ammo/clip/accuracy), consumables (gun oil, healing/shield potions), one-time gun unlocks (Rifle/Shotgun), and token buys (**Shield Booster** +50 max_shield, **Golden Gun**, **Exchange Token** — 1 horde token → `game_config.tokenExchangeGold` gold; the rate is baked into the entry's desc/msg at startup, after `--set` parsing).
- **Location actions & skills.** `LOCATION_ACTIONS` in db.js is the per-location catalogue — each entry: `key`, `label`, `timer` (s), `skill` + `skillLevel` gate, `successRate` %, `grants` (item on success), `xp` (skill XP on success), optional `requires` (a tool that must be *owned*, never consumed — mining copper needs a stone pickaxe, gathering mushrooms needs nothing). `POST /api/action/do {key}` validates location/skill/tool, marks the player busy for `timer` seconds (in-memory `ACTION_BUSY` map — a restart cancels running actions), and rolls the result via `setTimeout`, granting the item + skill XP as private `action` events. **Skills auto-level**: the skill pool (`s_<skill>_xp`) is progress toward the next level — `addSkillXp` rolls it over automatically (looping for big awards, cost = `skillLevelCost(next)` = `round(50 × lvl^1.4)`), emitting a private `level` event per level gained. **Every skill-XP award also adds the same amount to spendable `xp` and `lifetime_xp`** (skill training advances the main level and the leaderboard; spending never reduces lifetime). Main player XP is the universal spend: `POST /api/level/up` buys player levels, `POST /api/skill/up {skill}` buys the next skill level (`buySkillLevel` — costs `skillLevelCost(next)` from `xp`, leaves the skill's own progress pool untouched). The game page renders the location's actions (with Do buttons / busy countdown / requirement notes) in the Hunt Info//Actions card, and the Player Info modal lists all six skills with XP progress bars + a Level Up button when affordable. Skill columns are in `EDITABLE_STATS`, so the admin panel/CLI can edit them.
- **Rifle pierce:** when the horde is thick (`horde_size > RIFLE_PIERCE_MIN_HORDE`, 5), a successful rifle hit rolls a chance to drop a second zombie — 15% at 0 accuracy scaling linearly to 65% at 100 (`riflePierces()` + `RIFLE_PIERCE_*` constants in `server.js`). The kill event and toast call out the pierce.
- **Jamming is per gun, driven by condition.** Each shot rolls a jam after the round is spent: chance = `(100 − condition) × JAM_FACTOR` (0.25 in `server.js` — pristine guns never jam, condition 0 → 25%). A jam wastes the round, sets that gun type's `_jammed` flag, and blocks both shoot and reload until `/api/action/unjam` — which needs (and consumes) a clip, refilling ammo like a reload (`unjamGun` in `db.js`; the game page's Unjam button enables when jammed with clips left). Gun Oil is the prevention.
- **Golden Gun** is a temporary overlay, not an inventory gun: buying grants `golden_shots`. While `golden_shots > 0` the shoot handler uses it instead of the equipped gun — perfect hit, no ammo/jam/wear (it can't jam and ignores the real gun's jam), one zombie/shot — decrementing until spent, then reverting to the real gun.
- **Chat:** `/api/chat` posts a `chat` event; text is censored against a whole-word, case-insensitive list loaded from `file_config.censorFile` at startup (each hit → `****`).

**`item_backbone.js` — the item registry (pure data, no imports).** Single source of truth for every item and crafting recipe. `ITEMS` is keyed by the exact `player_inventory.item_name` string; each row: `name` (display), `type` (gun/tool/consumable/treasure/trade/crafting = `ITEM_TYPES`), `desc`, `value`, optional `use` (declarative effects — heal/shield/maxShield/gunCondition/gold/accuracy/goldenShots/tokens — applied by `applyItemEffects()`/`EFFECT_VERBS` in server.js; add a verb to the interpreter once, every item can use it), optional `shop: {cost, currency}` (listed in the in-game shop), `gunType` for guns (server.js derives `GUNS` from these), `tier` for tools ("Stone"/"Iron"/"General" — the Backpack's Tools column), and `toolbag: true` for quick-access combat consumables (gun oil, potions). `RECIPES` rows separate `inputs` (consumed, with quantities) from `requires` (a tool that's kept), and carry a `station`: `"campfire"` (player must have one burning) or `"forge"` (must be in Town). **`RANDOM_DROPS`** is the bonus-treasure table: rows (`key`/`name`/`chance`%/`value`/`desc`) auto-register into `ITEMS` as treasure; actions flagged `drops: true` in `LOCATION_ACTIONS` (the foraging/woodcutting ones) roll it top-to-bottom on success — first pass wins, one drop max, announced in the action's feed line. **Treasure sells from the Backpack**: `POST /api/inventory/sell {item, qty|"all"}` (treasure-type only, gold = registry `value` × qty, `sellItem` transaction in db.js, rows stay at qty 0); the Materials tab shows descriptions under each item and a Sell button on treasure opening a quantity-or-all modal. **Adding an item/recipe = adding a row** — server.js validates the whole registry at boot (types, effect verbs, every name referenced by `LOCATION_ACTIONS`/`RECIPES`/`STATIC_UPGRADES`) and FATALs on any unknown reference, so typos die at startup, not at runtime. The admin panel's Items tab and `GET /api/admin/items` are a read-only view. **Crafting**: `GET /api/craft` returns recipes annotated per-player (`lvlOk`/`stationOk`/`toolOk`/`inputsOk`); `POST /api/craft {key}` consumes the inputs up front (atomically via `consumeItems`) and grants output + skill XP when the timer resolves (shared `ACTION_BUSY`).

**`util/` — Admin CLI.** `index.mjs` runs a single command and exits when given argv (what the `menus/*.sh` dialogs call), else a readline REPL. `parser.mjs` routes `<group> <action> <args...>` to `commands/{users,players,inventory,database}.mjs`; `help` lists the groups and `help <group>` prints that group's commands with usage (backed by a `HELP` table in `parser.mjs` — update it when adding commands). Notable: `players stats|statsraw|getstat|setstat|forcelevel|guns|setgun` (the interactive editors in `menus/players.sh` — a stat menu with ±1/5/10/set, `level` special-cased to a full-stack `forcelevel` control, and a gun-equip menu with `setgun … force` — are built on the `*raw`/`guns`/`getstat` outputs), `users list|names|add|setpassword|setadmin|remove` (the `menus/users.sh` "List Users" opens a picker → per-user manage submenu), and the **`database` group** (`backup`/`backups`/`restore`/`migrate`/`inspect`, see toolkit below). `menus/lib.sh` provides the shared `pick_user` "Enter name/list" picker.

**Database toolkit** (`util/commands/database.mjs`, driven by `menus/database.sh`): introspects the freshly-built live DB as its **reference schema**, so it self-updates as the schema evolves. `backup` writes a timestamped `backup_database_<YYYYMMDD-HHMMSS>.bak` under **`util/backups/`** (gitignored, so wiping `data/` never touches them); `restore` picks from the list and copies over the live DB (closes the live handle, clears stale WAL/SHM); `migrate <path>` schema-verifies an old DB and brings it current in place (creates missing tables, adds missing columns with correct defaults) or reports it invalid. Backups use `better-sqlite3`'s online `.backup()` (safe while running); restore/migrate of the live DB assume the server is stopped.

**Logging.** `log(level, message, config, fileMessage?)` in `server.js`. Levels ascending: `FULL`(0, plumbing) < `INFO`(1, actions + tick results) < `WARN` < `ERROR` < `FATAL`. Console output requires `--verbose` and is colorized per level via `util.styleText` (auto-no-ops when the stream can't color; the log file stays plain). File writes happen in dev mode or for ERROR/FATAL. `FATAL` exits. **In dev mode, the console filter defaults to INFO** unless a level was explicitly set (`NONE` is the config default sentinel). A startup summary (mode/debug/tick/timeout) is always printed and logged, ungated; `timeout > 10` prints an "excessive" warning. **Sensitive-value redaction:** the optional 4th `fileMessage` arg is the version written to the log file — the console still shows the raw `message`, but the file gets the redacted one. Password/session lines (salts, the signed session cookie, payloads) pass `"…[redacted]"` for the file so nothing usable ever lands in `logs/server.log`. **Rotation:** the log is capped at `file_config.logMaxMB` (3MB); at the cap it rotates to `server.old.log` (replacing the previous rotation) with a `--verbose` console warning — checked once at startup and before every `log()` file write (the few direct `appendFileSync` writers rely on the startup check). `menus/logs.sh` can view the rotated file.

## Conventions & gotchas

- **Config is four objects in `config.js`:** `file_config` (log/db/censor filenames, `logMaxMB`), `ssl_config` (`enabled`, `certFile`/`keyFile` — see HTTPS below), `game_config` (verbose, dev, debugLevel, `sessionSecret`, timeout, heartbeatSeconds, baseMaxHealth, experimentResetHours, tokenExchangeGold), `zombie_config` (z_tic, z_chance, z_hit, z_damage, z_horde, z_raid). `sessionSecret` defaults to `'changeme'` and **must** be overridden for real deployments. Env overrides: `DB_PATH`, `PORT` (the old `HUNT_TICK_MINUTES` is gone). **`config.js` also exports `app_version` — the single source of truth for the version string** (startup summary + `--help` read it); only `changelog.md` and `README.md` state their own versions, and `package.json` deliberately has no `version` field.
- **Dev DB = delete & rebuild, no migrations.** This is a strictly dev build; when the schema changes, delete `data/zboe.sqlite*` and let `db.js` recreate it. Don't add `ALTER TABLE` migrations — real "old DB" migration is deferred to a future zboe2→zboe3 push. The two existing `ALTER`s (location/hidden) are legacy leftovers.
- `.gitignore` excludes `data/`, `logs/`, `util/`, `zboe.sh`, the install scripts, `package-lock.json`, `.env*`, and `*.sqlite`/`*.log` — so the Admin CLI (`util/`) is untracked, but `menus/` and `CLAUDE.md` are **tracked**. DB backups live under `util/backups/` on purpose (gitignored + survives wiping `data/`). Don't assume the working tree matches the repo.
- `scratchbook.js` / `scratchbook.note` are ignored scratch space, not part of the app.
- **`horde_size` (in `game_state`) is the single source of truth for the zombie count.** `horde_status` (`hiding`/`wandering`/`hunting`/`raiding`) comes from `hordeStatusOf()`, which reads the `raid_enabled` **latch** first (raid persists once triggered until the horde hits 0) then derives wandering/hunting from `z_horde`. `spawn`/`kill` events are narrative feed flavor, not counters.
- **Web admin & CLI share game logic via `db.js`.** `EDITABLE_STATS`/`setPlayerStat` (whitelisted, clamped stat writes) and the leveling rules are defined once in `db.js` and used by both `util/commands/players.mjs` and the `/api/admin/*` panel — change them there, not in two places.
- **Player location lives on `players.location`** (default `basecamp_outside`) — no `locations` table. The world is defined in `db.js`: `LOCATION_NAMES` (key → display name) and `LOCATION_LINKS` (the travel graph — Bunker hangs off Basecamp only; Forest is the hub to lake/mountains/river/swamp/cave/town). `POST /api/travel {to}` validates adjacency; `locationOf()` in `server.js` hardens unknown/NULL values to Basecamp. **`ZOMBIE_LOCATIONS` (db.js) gates all zombie contact**: basecamp (outside *and* inside — the base siege still works), forest, lake, swamp. Everywhere else is safe — the tick filters those players out entirely, and shoot/call-zombie 409 ("It's quiet here"). In safe zones the game page swaps the Hunt Info card to **"Actions"** (hunt stats hidden, location box stays) and disables Shoot/Call Zombie — and the Loadout card becomes the **Adventure Panel**: same HUD + Player Info, but gun stats/combat buttons swap for **Build Campfire** (consumes 2 firewood, burns 5 min — `CAMPFIRES` map in server.js, in-memory like `ACTION_BUSY`), **Cook Food** (modal of campfire-station recipes, enabled only while burning), **Put Out Fire**, and **Meditate on Magical Theory** (`POST /api/meditate` — safe zones only, 20s busy, +8 Magic XP). The **map modal lists only reachable locations**, each with a color-coded safe/zombies pill, and shows a base-HP pill when away from Basecamp (since the Base card is hidden there). `basecamp_inside` is the base interior — entered only via `/api/base/toggle` (which requires being at Basecamp), never via the map; while inside, the map is hidden and travel is refused. The game page's Map button (location box) opens a modal listing every location with Travel buttons on reachable ones; the Base card (health bar + toggle) renders only while `me.atBase`. `getLocationCount()` in `db.js` is still unreferenced — reserved for per-location occupancy/actions.
- **Backgrounding:** without `--verbose` the server daemonizes (self-respawn detached, writes `logs/zboe.pid`); `--stop` kills it. Only one backgrounded instance is tracked (single PID file), and a live PID file blocks a second background start. `menus/server.sh` drives this.
- **`sessionSecret` sanity halt:** while it's the default `'changeme'`, non-dev runs FATAL-exit at startup and dev runs only warn — set it before any real run.
- Several dead/duplicate `log(...)` calls sit after `return` in some route handlers (they never execute); don't treat them as reachable behavior.
