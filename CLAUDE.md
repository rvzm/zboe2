# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

zboe2 (Zombie Biohazard Outbreak Experiment 2) is a web-based multiplayer zombie-hunting game — a NodeJS/Express rewrite of an older IRC-based game. Early development (this is the first playable dev-rc after a prior build was lost to a drive failure). Pure ESM (`"type": "module"`), no build step, no test suite, no linter configured. Long-term direction: a text-based zombie-themed RPG with a traversal map of named locations (some zombie-threatened, some safe), a dynamic per-location actions panel, crafting/smithing, armor, spells, and resource gathering — `getLocationCount` in db_backbone.js is still an idle hook reserved for that. `public/img/` background art (one PNG per `LOCATION_NAMES` key, plus `page_playercard.png`/`page_admin.png` for those two static pages) is fully wired in — see `LOCATION_BG` in game.html and `#pageBg` in admin.html/playercard.html.

## Commands

```bash
npm run dev       # node server.js --dev -s -t -d   (stealth admins, fast timers, verbose+INFO)
npm run stable    # node server.js
npm run verbose   # node server.js --verbose
node util/index.mjs [group action args...]   # Admin CLI: REPL with no args, one-shot with args
npm run smoketest # node _smoketest.mjs — regression smoketest, see below
```

**`_smoketest.mjs`** (repo root, tracked) is a standalone regression smoketest — no test suite exists otherwise. It boots a fully isolated scratch instance (random port, a scratch DB under `os.tmpdir()` via a `DB_PATH` override, `--mock-db` seeded) so it never touches the real dev DB or collides with a separately-running `--dev` session, runs a battery of checks against the live API (auth, core gameplay, admin routes, plus a direct `item_backbone.js` registry-sanity check with no server needed), tears down, and exits 0 only if everything passed. The user has authorized Claude to create/update this file across sessions — add a check whenever a new route/feature is built, and run it after non-trivial changes to catch regressions before calling something done.

**`util/sanitycheck.sh.claude`** is a deeper, Claude-driven sanity check complementary to `_smoketest.mjs` (per-file syntax/import checks, the Admin CLI, direct SQLite inspection, a `boot` mode that stages a scratch server for a browser-driven follow-up pass) — output lands in `util/sanitycheck-notes.md`. Alongside it, three small gitignored (machine-local, `util/sanitycheck*`) files hold the user's own planning notes: **`util/sanitycheck.claude-instructions`** is durable — standing instructions the user accumulates over time and that persist across every future plan/session, checked at the *start* of every new plan, before design work begins; **`util/sanitycheck.claude-notes`** is scratch — "oh, this would be good to add" ideas jotted down while the user is mid-edit, *before* engaging Claude for a plan, also checked at the start of every new plan; and **`util/sanitycheck.claude-memory`** is cross-plan continuity — forward-looking tidbits Claude itself writes at the end of a plan/session (e.g. "this leaves X for a follow-up pass," "this will touch `game.html`/`admin.html` next") so a later plan/session has that context without re-deriving it, and is *not* cleared automatically the way `.claude-notes` is. At the start of planning any new task, read `.claude-instructions` and `.claude-notes` first (and `.claude-memory` if a prior session left anything relevant), cross-check their contents against the stated task, and surface any questions/conflicts/out-of-scope flags to the user *before* proceeding with deeper design — even when a note seems tangential to what's being asked, since a note that looks out of scope is exactly the kind of "hey, are you sure about X?" worth raising rather than silently ignoring or silently folding in. If both `.claude-instructions`/`.claude-notes` are still at their stock/placeholder content, say so explicitly and confirm the stated request is the complete scope, rather than inventing questions from nothing. As part of wrapping up a plan/session, clear `sanitycheck.claude-notes` back to just its header line so notes don't leak into the next plan — `sanitycheck.claude-instructions` is never cleared, and `sanitycheck.claude-memory` is only cleared/trimmed once its notes are no longer needed (e.g. a follow-up pass it was flagging is done).

Server listens on `PORT` (default 3000), over **HTTPS when `ssl_config.enabled`** (PEM `certFile`/`keyFile`, relative paths resolve from the project root; all cookies flip to `Secure` automatically; enabled-but-unreadable certs are a FATAL — no silent HTTP fallback, and the daemonizer pre-validates them before forking so the child can't die silently). The server manages its own foreground/background lifecycle (see `--verbose` / `--stop` below) — there is no systemd unit, and the Docker files were removed (they predated the self-backgrounding and never worked with it). The (gitignored) `install-*.sh` scripts install Node + npm deps, point at this lifecycle, and — if they detect nginx or Apache on the machine — print a ready-to-paste reverse-proxy snippet; the full proxy/HTTPS walkthrough is **`INSTALL.md`** (tracked). `./zboe.sh` is a `dialog` TUI: the Server menu starts/stops/restarts via `node server.js` / `node server.js --stop` (reading `logs/zboe.pid`), plus User/Player/Database/Log admin menus and the Admin CLI.

**Runtime flags** (parsed by a declarative `CLI_OPTIONS` table in `server.js`):
- `--dev` / `--production` (mutually exclusive).
- `-v` / `--verbose` — **foreground/background switch.** With it, the process stays attached as a live, colorized console. Without it, the process re-spawns itself detached, prints a couple of lines + the child PID, writes `logs/zboe.pid`, and releases the terminal.
- `--stop` — SIGTERMs the backgrounded server via `logs/zboe.pid` (handles missing/stale PID files).
- `--debug-level=<FULL|INFO|WARN|ERROR|FATAL>` and its alias `--debug=<LEVEL>` (the alias is real now — the old `--debug=` vs `--debug-level=` discrepancy is fixed).
- `--set group.key=value` (repeatable), `--group.key=value`, or bare `--key=value` — override any value in `file_config`/`game_config`/`zombie_config` for a single run, type-coerced to the existing value's type. Overrides are in-memory only; they don't write back to `config.js`.
- `--mock-db` — seeds a starter dev DB (`admin` + `player1` + `player2`, one admin) with random 5-char passwords, printed **to the console only** (never the log file). Idempotent — skips existing users.
- `-h` / `--help`.
- **Dev-only flags** (single letters, FATAL at startup if passed without `--dev`; `--dev -h` lists them — plain `-h` just prints a hint they exist): `-t` (every action/craft/meditation **busy timer** runs at 3s — deliberately *not* durations like campfire burn/spell buffs/sentry, which would break cooking; applied via `devTimerOf()` at both the resolve points and the `actionsFor`//api/craft display fields), `-s` (stealth admins: `players.hidden=1` on login and the tick's active-player filter skips admins entirely — no damage, targeting, base absorption, or death), `-d` (shorthand for `--verbose --debug-level=INFO`, normal last-wins vs an explicit level), `-a` (every registration is created an admin via `setUserAdmin`), `-H` (refill the horde to `z_horde` whenever it drops below — capital because `-h` is help), `-r` (same but to `z_raid`, keeping a raid rolling; wins over `-H` when both passed; both refill at the top of the tick, gated on `hunt_enabled`, and call `latchRaidIfNeeded`), and `-z N` (hard zombie cap on tick spawns / call-zombie (409) / refills — the admin panel's absolute set-horde deliberately bypasses it; accepts `-z 25` or `-z=25`, the one value-taking flag (`takesValue` in `CLI_OPTIONS`)). Active dev flags are appended to the startup summary (`devFlags=…`); state lives in the `DEV_FLAGS` object beside `CLI_OPTIONS`.

## Architecture

Three layers, with `db_backbone.js` as the hard boundary between the web layer and SQLite — plus a family of pure-data `*_backbone.js` leaf modules at the bottom of the stack (`item_backbone.js`, `magic_backbone.js`, `quest_backbone.js`, `location_backbone.js`) that `server.js` (and, where noted, `db_backbone.js` itself) imports. The `_backbone.js` suffix is a naming convention, not a purity guarantee: `item_backbone.js`/`magic_backbone.js`/`quest_backbone.js`/`location_backbone.js` really are zero-import pure data (plus, for `magic_backbone.js`, a few non-SQL helpers); `db_backbone.js` is named for family consistency but remains the real SQL/logic layer, not a leaf.

**`db_backbone.js` — the only place SQL lives, and the source of truth for game rules.** On import it opens/creates `data/zboe.sqlite` (WAL, foreign keys on), runs `CREATE TABLE IF NOT EXISTS` for the full schema, seeds the single `game_state` row (`key = 'main'`), and does a couple of legacy `ALTER TABLE` column-adds. It defines prepared statements once and exports thin named accessors. **Nothing outside `db_backbone.js` writes raw SQL** — the one exception is `util/commands/*.mjs`, which imports the raw `db` handle for admin ops. Add game state as a column/table + a matching exported accessor here, not as a query in `server.js`. Beyond accessors it also owns/exports: `GUN_TYPES`/`GUN_NAMES`, `DB_PATH`, the skills (`SKILLS`/`SKILL_NAMES`/`skillLevelCost`/`addSkillXp`/`spendSkillLevel`), the **`EDITABLE_STATS`** whitelist + `setPlayerStat` (used by both the CLI and the web admin), and the **leveling rules** (`nextLevelOf`/`prevLevelOf`/`levelCost`, `LEVEL_*_BONUS`, `applyLevelUp`, `forceLevel`). Put shared game math here, not duplicated in `server.js` or the CLI. It imports `ZOMBIE_LOCATIONS` back from `location_backbone.js` (below) since two of its own accessors — `adjustLocationZombies`, `updatePlayerLocation` — validate against it internally; this is the one `*_backbone.js`-importing-another-`*_backbone.js` edge in the stack.

**`location_backbone.js` — the world/location registry (pure data, no imports).** Split out of `db_backbone.js` during the server.js reorganization. Owns `LOCATION_NAMES` (its keys are the canonical location list), `LOCATION_LINKS` (the travel graph), `ZOMBIE_LOCATIONS` (the 4 locations where zombie contact/the tick/hunting are active), `OUTBREAK_LOCATIONS` (8 locations — the always-active `ZOMBIE_LOCATIONS` plus the 4 normally-safe ones the Zombie Outbreak mode makes unsafe — see Zombie Location Pool below), and `LOCATION_ACTIONS` (the per-location action catalogue). `SKILLS`/`SKILL_NAMES`/`skillLevelCost` stayed behind in `db_backbone.js` — they're general-purpose (used well beyond locations), not location data.

**DB provenance stamp** (`computeDbStamp`/`ensureDbStamp`/`rotateDbStamp` in db_backbone.js) — a second, distinct use of `session_key`/`session_id`, this time on `game_state`, `player_inventory`, `events`, and `nuke_votes` (unrelated to the anti-hijack cookie pair on `users`/`players` above). It's a **deterministic** fingerprint of `(game_config.sessionSecret, path.basename(DB_PATH))` — not random, so the same deployment reproduces the same stamp across restarts — written onto every row this app inserts into those four tables, so a row (or the whole DB file) that didn't come from an app instance sharing this secret+filename can be told apart from one that did: a swapped-in DB, or rows written directly by something that doesn't know the secret. `computeDbStamp()` is **never memoized/called at module load** — server.js applies `--set game_config.sessionSecret=...` overrides *after* importing db_backbone.js (ES module imports evaluate before the importing module's own top-level code), so an eager computation would freeze in the pre-override secret; it reads `game_config.sessionSecret` fresh on every call instead (the config object is shared by reference across both modules). For the same reason, `insertEvent`'s INSERT is prepared **inline, not as a module-level cached statement** — a `db.prepare()` at module scope runs unconditionally at import, which would crash *every* server.js invocation (even `--help`) against a DB that predates these columns, before any of the checks below get a chance to run.

`server.js` calls `hasProvenanceColumns()` first (FATAL, both modes, if the columns don't exist yet — points at `database update` or a dev delete-and-rebuild) then, in the normal path, `ensureDbStamp()` once at startup after CLI overrides are applied: a `game_state` row still holding the schema's column defaults has never been stamped (fresh DB, or one just migrated to add the columns) and gets genesis-stamped right then (logged INFO); an already-stamped row is only ever *compared*, never overwritten, so a mismatch — rotated secret/filename, or a genuinely unexpected DB — survives as evidence and follows the same **dev-WARN / production-FATAL** split as the `sessionSecret === 'changeme'` check beside it.

**`--rotate-keys`** is the deliberate-rotation counterpart: a one-shot maintenance flag (pair it with a new `sessionSecret` in config.js or `--set game_config.sessionSecret=...`) that re-keys *every* row across all four tables to whatever the current secret+filename computes, then exits — it never continues on to start the server. It always WARNs (never FATALs, in either mode — this is the requested action succeeding, not an anomaly): `"Forcing DB Key rotation, re-keying database"` plus a per-table row count if the DB's stamp was actually stale, or `"...nothing to rotate"` (leaving every row untouched) if it already matched what this run would compute. There's no way to rotate only *some* rows or preview the change first — it's all-or-nothing by design.

Core tables:
- `users` — auth (`is_admin`, `pass_salt`/`pass_hash`, `last_login`) plus the moderation gates (`adm_fun`, `chat_mute`/`chat_deaf`/`chat_strict`, `login_restricted`+`login_res_time`/`login_res_set_time`/`login_res_reason`, `user_exiled`, `failed_login_count`/`failed_login_lockout_until` — see moderation below).
- `players` — 1:1 stats. `xp` (spendable) + `lifetime_xp` (leaderboard rank) + `level`; `health`/`max_health`; `shield`/`max_shield` (shield caps at `max_shield`, not a fixed 100); `golden_shots` (Golden Gun power-up counter); `accuracy`, `kills`, `gold`, `horde_tokens`, `equipped_gun`, `equipped_armor` (registry armor name, `''` = none — one slot, equipping swaps), `location`, `hidden`, `last_seen`; `forge_fired` (0/1 — the player's Mountains forge is lit; **persistent**, unlike the in-memory campfire, until put out / admin-toggled / death); `beacon_fired` (0/1 — live Bunker supply beacon, same pattern, cleared when the drop is redeemed). **Ammo/clips/condition/jam are per gun type**: `handgun_*`, `rifle_*`, `shotgun_*` (`_ammo`, `_max_ammo`, `_clips`, `_max_clips`, `_condition`, `_jammed`) — there is no player-level `jammed` flag; a jammed Rifle doesn't stop the Handgun. Page stats read from whichever gun is equipped. **Skills are per-skill column pairs**: `s_<skill>_lvl`/`s_<skill>_xp` for every entry in `SKILLS`/`SKILL_NAMES` in db_backbone.js (magic/defense/woodcutting/fishing/mining/smithing/crafting/foraging/trapping/alchemy/cooking). `ap_level` is the innate **"Base AP"** stat (default 0, wiped by death like everything else): `armorApOf()` adds it on top of equipped-gear AP and spell buffs, it's bought +10 at a time via the **AP Base** upgrade (below), and it's in `EDITABLE_STATS` so the admin panel's Core stats table and the CLI can set it. The **Defense skill** trains two ways — the *Train Defense* action (Town & Forest, 10s, +15 XP, always succeeds) and **taking zombie damage**: the tick awards Defense XP from the post-armor `dealt` (nothing when fully blocked) — `max(1, floor(dealt/10))` while raiding, `max(1, floor(dealt/5)×3)` for hunting/wandering — and gates **wearing armor**: each registry armor carries a `defense` level (bronze 1, iron 5, silver 10, gold 15, gold+silver 20, mythril 25, adamantite 30, syllic 35; boot-validated), enforced by `/api/armor/equip` and shown as a Def badge (red when unmet, Equip disabled) in the Backpack/playercard Armor tabs. The game HUD shows an **AP pill** next to the player name (gear + spell buff + `ap_level`, from game-state's `me.armorAp`).
- `player_inventory` — items (guns are inventory items; a consumed consumable stays at qty 0, visible-but-unusable).
- `player_magic` — magic knowledge, one row per learned spell (`type` is `'spell'` for now — the column leaves room for future magic rows; `name` = a `MAGIC_SPELLS` key; unique on `(user_id, type, name)` so grants are idempotent). Starters (magic_backbone.js `STARTER_SPELLS`, currently `magic missle`) are granted in `insertPlayer`, wiped + re-granted through `resetPlayer` on death, and backfilled for all players at every boot. Accessors: `getPlayerMagic`/`knowsSpell`/`learnSpell`.
- `events` — global feed. `type` (spawn/kill/shoot/attack/death/chat/system/level/item/shop/reload/travel/action), `visibility` (public/private/background — `background` is hidden from the feed), and `target` (`'global'` or a stringified `user_id`; the feed query returns global + your own).
- `game_state` — one `key='main'` row: `hunt_enabled`, `horde_size`, `horde_status`, `raid_enabled`, `online_players`, `base_health`, `base_destroyed_at`.
- `nuke_votes` — ballots while the base is destroyed. (There is no items table — the item catalogue is code, see `item_backbone.js` below.)

**`server.js` — Express app, auth, game-state API, and the game tick.** Session auth is a hand-rolled signed cookie (`zboe_session`): base64url JSON + HMAC-SHA256 keyed on `game_config.sessionSecret`; passwords are PBKDF2-SHA256. **On top of that sits a server-side session pair** (anti-hijack): login/register mint a random 25-char key + UUID; the key is HMAC-salted with `sessionSecret` before storage (the DB never holds the raw value), written to *both* `users` and `players` (`session_key`/`session_id`, defaults = the logged-out state `'LOGGED_OUT'` + 64 zeros), and carried by the browser as `zboe_skey`/`zboe_sid` httpOnly cookies (sent automatically — no page code involved). `requireAuth` verifies cookie-vs-stored *and* users-vs-players agreement; any mismatch logs a **WARN** with the IP and bounces to login. Logout voids the pair (`LOGGED_OUT` + zeros); a login against a non-logged-out session is **blocked while that session is active** (`last_seen` within `timeout`) and silently replaces it when stale — rotation kills the old cookies. `resetPlayer` copies the pair back onto the fresh players row so dying doesn't end the session. `requireAuth` populates `req.user`/`req.userId`, plus **`req.gates`** (`admFun`/`chatMute`/`chatDeaf`/`chatStrict`, read fresh from `users` every request); `requireAdmin` (checks `users.is_admin`) gates admin-only routes (hunt toggle, base reset, and the whole `/api/admin/*` panel API). The main frontend is one static page (`public/game.html`) that polls `GET /api/game-state` every 3s and composes one JSON response (player stats, world/base status, leaderboard, filtered events, online list). The page splits events into two feeds: **"Your Activity"** (left sidebar) shows the player's own `PERSONAL_TYPES` events (shoot/reload/shop/item/travel/action); the middle **World Feed** shows everything else (spawns, kills, attacks — including base attacks — deaths, chat, system, level-ups). **Level-ups (player and skill) are public `level` events** broadcast to everyone via the World Feed: `"<player> increased to level <N>!"` (`/api/level/up`, `/api/level/max`) and `"<player>'s <Skill> skill increased to level <N>!"` (auto-leveled in `addSkillXp`/db_backbone.js, or bought via `/api/skill/up`). The navbar shows `app_version` (sent in game-state), a Logout button, and — for admins with the **`adm_fun`** sub-permission specifically (`users.adm_fun`, separate from `is_admin` — grant/revoke from the Users tab; gated server-side by `adminFunReq` on top of `adminReq`) — a **🎉 Fun button** opening the Admin Fun modal (`POST /api/admin/fun {what}`): self-targeted cheats `boost` (level 99 via `forceLevel`, 100k gold, 100 tokens, every gun, max accuracy), `items` (99 of every registry item), `ammo` (all guns 99/99 ammo+clips), `vitals` (health/shield 1000, filled) — all through the same whitelisted `setPlayerStat` helpers — plus `nuke` (clears the horde, drops the raid latch, announces a public world event). **Inventory is its own modal** (not a shop tab): **Toolbag** (registry `toolbag` consumables with Use buttons, greyed at qty 0) and **Backpack**, which nests type sub-tabs with type-specific columns — Guns (live cond/ammo/clips from the player row via `/api/inventory`'s `guns` array, jam badge, Equip), **Armor** (`armors` array: AP badge, condition pill (gun-style tiers), qty, Equip/Unequip via `POST /api/armor/equip` — one slot, `item: ""` strips — and Sell; `/api/inventory/sell` accepts treasure *and* armor, but the worn set can't be sold: while equipped only qty−1 is sellable), Tools (tier badge), Consumables (non-toolbag food, qty + Use), Materials (crafting/trade, qty), and Treasure (value + Sell on every row — treasure no longer shares the Materials tab). Level Up/Max buttons live in the Player Info modal, not the main HUD; the HUD statcard stacks health (red) / shield (blue) / mana (purple) / **XP (gold, progress toward `nextLevelCost`)** bars. The right sidebar's **Players card combines the XP leaderboard and online presence**: the rank badge is green (online) or grey (offline), usernames use the level-tier shimmer gradient (`.shiny-name`, shared with the HUD name), and online players outside the top list are appended unranked. There is also a **web admin panel** at `/admin` (`public/admin.html`, admin-gated) — backed by `/api/admin/*` endpoints, and **live-updating**: a 3s `setInterval` always refreshes World-tab data (so the destroyed-base banner and Base/Horde boxes stay current from any tab) and additionally re-loads whichever other tab is active (Users, or Players — list or the open Edit Player view; the read-only Items tab never changes at runtime, so it's not polled). Tabs: **World** (default — live hunt/horde/base state with toggle-hunt, set-horde-size (`POST /api/admin/world/horde`, keeps the raid latch coherent, plus **+/-1/5/10 delta buttons** alongside the absolute-size input), reset-experiment, the **Base box** (sentry-status + repair-kits pills, a **Refill Base Health** button (full heal, free) and **Activate Free Sentry** button (4h, free) via `POST /api/admin/world/base/repair`/`base/sentry` — both 409 on a destroyed base and disabled client-side to match), and an online-player table with location + safe/zombie + busy/campfire badges from the in-memory maps, via `GET /api/admin/world` (now also carrying `base.repairKits`/`sentryActive`/`resetAt`, and a `events` array — the conversational subset only, `chat`/`admin_chat`/`system`, unfiltered by the viewing admin's own chat gates since this is a moderation surface). Below that, a two-column row: **World Chat & Events** (the feed above, plus a send box — `POST /api/admin/chat {message, target?}`, its own `admin_chat` event type so it can be told apart from player chat; blank `target` broadcasts `"[Admin] text"`, a specific username addresses `"[Admin->user] text"` — always public) and **Users** (level/online/location/safe-or-zombies + inline mute/deaf/strict/ban/exile badges, from the same enriched `listUsers()` the Users/Players tabs use), each row's **Actions** button opening a modal with: chat-gate toggles (`POST /api/admin/moderation/chatflag {username, flag: mute|deaf|strict, value}`), a temp ban (duration dropdown 1m→72hr plus custom, optional reason defaulting to `"Admin <admin> Placed a <duration> ban on you"`, `POST /api/admin/moderation/ban {username, seconds, reason}`) with Unban, and Exile/Un-exile (`POST /api/admin/moderation/exile`/`unexile` — exile is permanent and always clears any active temp ban first). **Users** (CRUD, plus a Grant/Revoke Fun button per admin row for `adm_fun`); **Players** (a full player list — level/location/online, enriched via `listUsers`'s players join — that swaps to the Edit Player view on click; a **Player Card** mirroring the game HUD (level circle + health/shield/mana/XP bars) with quick-edit rows beneath it for health/max/shield/max/mana/max/gold/tokens (±/set plus **Refill** on health, shield & mana = set to the matching max) — those eight fields are excluded from the stats table, which stays grouped Core/per-gun/Skills with prefixes stripped; `forceLevel` control, a location teleport dropdown (`POST /api/admin/player/location` — bypasses the travel graph), gun equip, and inventory grants via a registry-driven dropdown); **Items** (read-only registry/recipes/static upgrades). A **destroyed-base warning banner** (below the navbar, above the tabs — visible on every tab, not just World) reads "⚠️ WARNING! Base destroyed! `<countdown>` Until Base Resets", the countdown formatted client-side every second from `base.resetAt` (`base_destroyed_at + experimentResetHours`, computed server-side so the client never needs the config value). **Every admin action that mutates another player or world state announces itself as a public `system` event** (`[Admin] <admin> <did the thing>` — teleport, any stat change (with increased/decreased/toggled wording and a `%` suffix for accuracy), force-level, gun equip/force-equip, inventory grant/take, user add ("...Welcome our new companion and wish them luck!")/delete, horde-size change (with the resulting hunting/wandering/raiding status), the free base-repair/sentry actions above, and every moderation action (chat-flag toggle, ban, unban, exile, unexile)) — self-targeted admin actions (the 🎉 Fun modal, password resets, admin-flag/adm_fun grants) are not announced this way. The pre-login landing page (`public/index.html`) shows a live leaderboard from **`GET /api/leaderboard`, the one unauthenticated API endpoint** (rows: `{user, xp: lifetime_xp, level}`; optional `?limit=` — default 25, capped at 500).

**`public/playercard.html`** is one file serving two modes off a single query param. **No `?p=`** — a fancier public leaderboard (same `/api/leaderboard`, `?limit=100`, no login needed — mirrors index.html's unauthenticated access), gradient-colored usernames (`nameClassForLevel`, duplicated from game.html — same tier thresholds/CSS so a given level always shimmers the same color everywhere), each row's **View** button linking to `?p=<user>`. **`?p=<user>`** — a read-only profile card for *that* username (not just the caller), **publicly viewable** (playercard.html is a plain `express.static` file like index.html — no custom route). Backed by `GET /api/playercard?user=<name>` (also not behind `requireAuth`; 404 if no such user) — an anonymous visitor still gets a card, just a stripped one: the response's **`authenticated`** flag (from **`tryAuth(req)`**, a non-redirecting sibling of `requireAuth` — same cookie/session-pair verification, `null` instead of a redirect on failure, kept as a separate function specifically so `requireAuth`'s granular hijack-detection WARN logging never had to be touched) gates a big `Object.assign` block: logged out, the payload is only level/health/shield/mana/kills/accuracy/skills/rank — gold, tokens, location, lifetime XP, gun oil count, and every inventory category are **withheld server-side**, not merely hidden client-side. playercard.html matches its UI to that flag: the Currency and Location boxes and the Backpack/Toolbelt/Potions panel (swapped for a "Please login to view this data" notice, `#mainLoginPrompt` vs `#mainAuthedContent`) disappear outright, and Survival drops to just Kills/Accuracy (`#svAuthOnly` hides the Lifetime XP/Gun Oil/Guns rows) — reuses the same gun/armor-enrichment logic as `/api/inventory` but keyed off an arbitrary looked-up user id, plus survival (kills/accuracy/lifetime XP/gun oil count/owned guns as pills — the equipped one blue (`text-bg-primary`), the rest neutral dark, from `guns` not the flat `gunsOwned` since only the former carries `.equipped` — each stat on its own divider-separated line)/currency (gold — gold-colored pill; tokens — purple pill, since Bootstrap has no built-in purple badge; both sized up via a `.stat-tile-lg` modifier, also applied to Location)/location(+safe-or-zombies)/leaderboard-standing and all ten skills (read-only — no Buy button; you can't spend someone else's XP). The leaderboard-standing tile shows a large (4rem) glyph on top — 🥇/🥈/🥉 for #1-3, a random wave (`WAVING_EMOJI`) for #4-9, ☣️ for #10+ and unranked — with the `"#N of M"` text (`db_backbone.js`'s **`getLeaderboardRank`**: exact rank via the same tie-break order as the leaderboard query, lifetime_xp DESC → level DESC → username ASC, plus total player count) at the bottom. No action endpoints hang off this page at all — equip/use/sell only ever work on your own inventory via the existing routes. Layout: a header box (level circle + shiny-name + health/shield/mana bars, then four stat tiles) above a sidebar (skills) + main panel with four tabs — **Backpack** (Guns/Armor/**Materials**/Treasure/Food/Base behind vertical category buttons — Food is non-toolbag consumables, i.e. cooked meals; **Materials groups under a header row per metal** — item_backbone.js's `SMELT_TYPES`, sent to the client in the same `/api/playercard` payload, matched by name prefix so "copper ore" *and* "copper wire" both land under "Copper" — anything that doesn't match a metal family falls into a trailing "Other" group), **Toolbelt** (flat Tools list), **Potions** (flat list of the *toolbag* consumables minus gun oil, which is a Survival stat instead of an inventory row), **Spells** (the spells this player has learned — `player_magic`, from the auth-gated `spells` array) — a split of the game page's backpack categories chosen so nothing overlaps and nothing's left out.

- **Game tick** (`startZombieTicker`, every `zombie_config.z_tic` s): spawns (`z_chance%`, **doubled during a raid**) then runs an attack tier — **wandering** (<`z_horde`: one zombie @ `z_hit%`), **hunting** (≥`z_horde`: up to 75% of zombies hit every active player), **raiding** (≥`z_raid`: each zombie @ `z_hit/2%` hits up to 10 players for double damage). Damage is shield-first then health (`damagePlayer`) — but first the tick's tallied total is checked against the player's AP as a **final hit calc**: armors carry an `ap` (1-500 gauge), `armorApOf` sums equipped-gear AP + spell-buff AP + innate `ap_level`, and `ap/500` of the total is blocked (`apBlocked` in server.js; the attack event reports what was blocked, and damage that lands trains the Defense skill — see the players-table bullet). Inside players are absorbed by the base (2 base HP each, up to 500) and their armor pools into **Base AP** (`baseApOf`, shown as a pill on the Base card and sent in game-state's `base.ap`), which deflects base damage with the same formula, capped at `BASE_AP_MAX_BLOCK` (90%) so the base can't be made invincible; every surviving base hit emits a public world event (`The base was attacked for N (X/max HP)`); base death resets everyone inside; an outside player at 0 HP dies. Death = full reset to level 1 (`resetPlayer`). A destroyed base freezes the world until an admin reset, a passed nuke vote, or `experimentResetHours` elapse — then `experimentReset` wipes global state.
- **Raid is a latch, not a threshold.** Once the horde reaches `z_raid` it latches `raid_enabled` on (`latchRaidIfNeeded()`, called after every zombie add — tick spawn & call-zombie) and stays raiding until the horde is fully **cleared to 0** (handled in the shoot handler), regardless of dropping back below `z_raid`. `hordeStatusOf()` reads the latch first.
- **Hunt vote** — non-admins' path to flipping `hunt_enabled` without an admin (`POST /api/hunt/toggle` stays admin-only, `requireAdmin`). `POST /api/hunt/vote/start` opens a 30s Yes/No poll (`HUNT_VOTE_SECONDS`), toggling whichever direction is opposite the current state (same semantics as the direct button) — one vote globally at a time (409 if already running), state is **in-memory only** (`HUNT_VOTE`, same restart-clears-it convention as `ACTION_BUSY`/`CAMPFIRES`/`SPELL_ARMOR_BUFFS`). `POST /api/hunt/vote/cast {vote}` records/overwrites the caller's ballot (changeable up to the deadline) — an **admin's** vote is publicly announced (`[Admin] <user> voted YES/NO on the hunt vote.`), a regular player's is silent (tallied only). Passes with **at least one Yes** and either no dissent or Yes strictly outnumbering No; otherwise the public event is exactly `"The vote was majority no."` (`resolveHuntVote`, guarded against stale timers via reference-equality on `HUNT_VOTE`). An admin's direct toggle mid-vote **cancels** it (`cancelHuntVote`) so a stale vote can't flip the hunt back against a fresh admin action. `GET /api/game-state`'s `huntVote` field (`huntVoteStatus()`) carries the live tally/countdown/`myVote` plus `onlineNonAdminCount` (online players who aren't admins) — the game page's Yes/No buttons use it to gate an admin's cast behind a `confirm()` once more than 5 non-admins are online ("there are enough players to decide on their own"), same destructive-confirm pattern admin.html uses elsewhere. UI: `#btnHuntVoteStart` (non-admins only, hidden mid-vote) sits where `#btnHuntToggle` (admins) lives; `#huntVotePanel` (countdown badge + live Yes/No counts) shows to everyone while a vote is active.
- **Tokens (`horde_tokens`):** the shooter who lands the horde-breaking kill (crossing below `z_horde`, non-raid) earns **+1**; the kill that clears the last zombie during a raid earns **+3**. Raid supersedes horde (no double award).
- **Leveling** (`/api/level/up`, `/api/level/max`): levels are strictly numerical (always +1); cost compounds (`levelCost = round(100 × level^1.6)`). **Stat bonuses (+5 accuracy capped at 100, +5 max health, heal to new max) apply on every level through 15, then only every 5th level (20, 25, …)** — `levelGrantsBonus()` in `db_backbone.js` decides; `applyLevelUp` returns a `bonus` flag the level-up message uses. `lifetime_xp` (the leaderboard rank) is untouched by spending. Admin `forceLevel` applies/reverses the same conditional bonuses without an XP cost. Rules live in `db_backbone.js`.
- **Presence:** `last_seen` is touched **only** by the game-state poll (the page's active refresh) and at login — actions no longer touch it. `online` = `getActivePlayers` within `game_config.timeout` seconds; drop by lowering `timeout`.
- **Shop = two sources, both code-defined.** Registry items with a `shop: {cost, currency}` block in `item_backbone.js` (`/api/shop`, `/api/shop/buy` by ITEMS key — currently the tools; `purchaseItem` in db_backbone.js is the transaction) plus the hardcoded `STATIC_UPGRADES` list in server.js (`/api/shop/upgrades`, `/api/shop/upgrades/buy` by `key`). Each static entry has a `category` (`"upgrade"` → Upgrades tab; `"item"` → Shop tab alongside registry items) and a `currency` (`"gold"`, `"token"`, or `"mana"`), plus optionally **material `inputs`** (`{ item: qty }`, consumed atomically via `consumeItems` — checked/spent *after* the currency check so a missing ingredient never eats the mana) and a **`defense` skill gate**. The one mana entry so far is **AP Base** (`ap_base`: 25 mana + 10 firewood/5 copper ore/3 glowcap, Defense 2+, repeatable — each buy is a permanent +10 `players.ap_level`); `GET /api/shop/upgrades` annotates entries with a per-player `affordable` flag (inputs owned + defense met) since the shop client can't count inventory, and the buy handler 409s each unmet gate separately. The Shop tab has Backpack-style category sub-tabs — Consumables / Guns / Tools / Tokens — derived client-side (`shopCatOf`: token currency → Tokens, then by type). Covers stat boosts (equipped-gun ammo/clip/accuracy), consumables (gun oil, healing/shield potions), one-time gun unlocks (Rifle/Shotgun), and token buys (**Shield Booster** +50 max_shield, **Golden Gun**, **Exchange Token** — 1 horde token → `game_config.tokenExchangeGold` gold; the rate is baked into the entry's desc/msg at startup, after `--set` parsing).
- **Location actions & skills.** `LOCATION_ACTIONS` in db_backbone.js is the per-location catalogue — each entry: `key`, `label`, `timer` (s), `skill` + `skillLevel` gate, `successRate` %, `grants` (item on success), `xp` (skill XP on success), optional `requires` (a tool that must be *owned*, never consumed — mining copper needs a stone pickaxe, gathering mushrooms needs nothing), optional `uses` (an item **consumed ×1 up front**, committed even if the roll fails — smelting burns ore, firing the forge burns firewood), optional `station` (`"campfire"`/`"forge"` — the same `stationOk` gate as recipes; the mountains smelt actions carry `station: "forge"`), optional `activates: "forge"` (success sets `players.forge_fired` via `setForgeFired` instead of granting an item — mutually exclusive with `grants`; see the mountains `fire_forge` action), optional `trainOnly: true` (XP-only — no grant/activate required, the *Train Defense* rows), and optional `text` (custom start-event line replacing "You started: <label>"). **A row can instead be a recipe pointer — `{ recipe: "<RECIPES key>" }`** (or a `{ key, button: true, label }` **UI-button row** — a plain button in the Actions card that opens a page modal, e.g. Town's Magic Table; see magic_backbone.js below) — surfacing an item_backbone.js recipe in that location's Actions card: `actionsFor` expands it from the recipe (label/timer/skill/inputs/tool/station, `successRate` 100 — crafts always land) and `/api/action/do` delegates it to `handleCraft`, the same flow as `POST /api/craft`. All the forge smelting/armor-smithing rows at the mountains are recipe pointers — don't hand-roll an action that duplicates a recipe (`uses` is for single-item fuel like `fire_forge`'s firewood; the validator rejects object-form `uses`). `POST /api/action/do {key}` validates location/skill/tool/station/uses, marks the player busy for `timer` seconds (in-memory `ACTION_BUSY` map — a restart cancels running actions), and rolls the result via `setTimeout`, granting the item + skill XP as private `action` events. **Skills auto-level**: the skill pool (`s_<skill>_xp`) is progress toward the next level — `addSkillXp` rolls it over automatically (looping for big awards, cost = `skillLevelCost(next)` = `round(50 × lvl^1.4)`), emitting a private `level` event per level gained. **Every skill-XP award also adds the same amount to spendable `xp` and `lifetime_xp`** (skill training advances the main level and the leaderboard; spending never reduces lifetime). Main player XP is the universal spend: `POST /api/level/up` buys player levels, `POST /api/skill/up {skill}` buys the next skill level (`buySkillLevel` — costs `skillLevelCost(next)` from `xp`, leaves the skill's own progress pool untouched). The game page renders the location's actions (with Do buttons / busy countdown) in the Hunt Info//Actions card — **`actionsFor` filters to actions the player can run right now** (skill, tool, `uses`/inputs owned, station usable, station not already lit); locked ones simply don't appear until unlocked (the card shows a "nothing you can do here" note when empty, and the do-handler still enforces every gate server-side), and the Player Info modal's Skills tab (paired with a Spells tab — see magic_backbone.js below) lists every skill with XP progress bars + a Level Up button when affordable. Skill columns are in `EDITABLE_STATS`, so the admin panel/CLI can edit them.
- **Rifle pierce:** when the horde is thick (`horde_size > RIFLE_PIERCE_MIN_HORDE`, 5), a successful rifle hit rolls a chance to drop a second zombie — 15% at 0 accuracy scaling linearly to 65% at 100 (`riflePierces()` + `RIFLE_PIERCE_*` constants in `server.js`). The kill event and toast call out the pierce.
- **Jamming is per gun, driven by condition.** Each shot rolls a jam after the round is spent: chance = `(100 − condition) × JAM_FACTOR` (0.25 in `server.js` — pristine guns never jam, condition 0 → 25%). A jam wastes the round, sets that gun type's `_jammed` flag, and blocks both shoot and reload until `/api/action/unjam` — which needs (and consumes) a clip, refilling ammo like a reload (`unjamGun` in `db_backbone.js`; the game page's Unjam button enables when jammed with clips left). Gun Oil is the prevention.
- **Golden Gun** is a temporary overlay, not an inventory gun: buying grants `golden_shots`. While `golden_shots > 0` the shoot handler uses it instead of the equipped gun — perfect hit, no ammo/jam/wear (it can't jam and ignores the real gun's jam), one zombie/shot — decrementing until spent, then reverting to the real gun.
- **Chat:** `/api/chat` posts a `chat` event; text is censored against a whole-word, case-insensitive list loaded from `file_config.censorFile` at startup (each hit → `****`). `users.chat_mute` 403s the post entirely. Two more gates filter what a player *receives* (applied in `/api/game-state`, on top of `getRecentEvents`): `chat_deaf` drops both `chat` and `admin_chat` events; `chat_strict` drops only regular `chat`, leaving admin-authored `admin_chat` visible (deaf wins if a player somehow has both).

- **Account moderation (`users` table gates).** Beyond `is_admin`: `adm_fun` (Fun-button sub-permission, above), `chat_mute`/`chat_deaf`/`chat_strict` (above), `login_restricted` (a temp ban — `login_res_time` seconds from `login_res_set_time` epoch ms, `login_res_reason`; auto-lifts on the *next login attempt* after it expires, no timer needed — `POST /login` checks `Date.now() < set_time + time*1000` and calls `unbanUser` if it's passed), and `user_exiled` (permaban — checked *before* the temp ban and before the password, and **always clears** any active temp ban when set, per `exileUser` in db_backbone.js). Login precedence: exile → temp ban → the automatic failed-attempt lockout below → password. Ban/exile messages surface via the existing `?err=` query-string flash on `login.html` (now `white-space: pre-line`, since the ban message is two lines: the lift time, then the reason). Independent of all that, **`account_config`** (config.js, `--set`-able like the other groups) drives an automatic lockout: `failed_login_max` (default 5) bad passwords in a row sets `failed_login_lockout_until` for `failed_login_lockout_seconds` (default 300 = 5m) — a *security throttle*, not a moderation action, so it's tracked/messaged separately from `login_restricted` and never touches it. `setChatFlag`/`setAdmFun`/`banUser`/`unbanUser`/`exileUser`/`unexileUser`/`recordFailedLogin`/`resetFailedLogin` in db_backbone.js back all three surfaces (CLI, TUI, admin page) — see `users ban|unban|exile|unexile|admfun|chatflag` (`util/commands/users.mjs`; `ban`/`exile` take a freeform trailing reason, `ban`'s duration parses `30m`/`24h`/`3d`/bare-seconds, defaulting to `account_config.ban_timeout`) and `menus/users.sh`'s per-user "Ban / Unban / Exile" submenu (same duration presets as the admin page).

**`item_backbone.js` — the item registry (pure data, no imports).** Single source of truth for every item and crafting recipe. `ITEMS` is keyed by the exact `player_inventory.item_name` string; each row: `name` (display), `type` (gun/tool/consumable/armor/treasure/trade/crafting = `ITEM_TYPES`), `desc`, `value`, optional `use` (declarative effects — heal/shield/maxShield/mana/gunCondition/gold/accuracy/goldenShots/tokens — applied by `applyItemEffects()`/`EFFECT_VERBS` in server.js; add a verb to the interpreter once, every item can use it), optional `shop: {cost, currency}` (listed in the in-game shop), `gunType` for guns (server.js derives `GUNS` from these) plus an optional `attack_mod: { dmg?, floor?, acc? }` letting an individual gun item vary from its `gunType`'s shared `WEAPON_FIREARM_EXPORT` stats — `dmg`/`floor` are additive offsets to those base fields (`dmg` only has a real effect in Nearby-scope combat; Broad/World/Location kills are instant and never read it), `acc` is a flat post-formula hit-chance handicap/bonus (`server.js`'s `computeHitChance`, clamped to `[0,100]`) — `equippedGunConfig()` merges base + mod once per shot; a gun with no `attack_mod` resolves to the base object unchanged. `ap` for armors (1-500 effectiveness gauge — server.js derives `ARMORS` and validates the range at boot; see the tick's armor hit calc), `tier` for tools ("Stone"/"Iron"/"General" — the Backpack's Tools column), and `toolbag: true` for quick-access combat consumables (gun oil, potions). `RECIPES` rows separate `inputs` (consumed, with quantities) from `requires` (a tool that's kept), and carry a `station`: `"campfire"` (player must have one burning), `"forge"` (the player's **Mountains forge** must be fired — `players.forge_fired`, lit via the `fire_forge` location action, put out via `POST /api/forge/toggle`), or `"beacon"` (a live **Bunker supply beacon** — `players.beacon_fired`, lit via the `activate_supply_beacon` action's `activates: "beacon"`, and **spent again when a beacon-station craft resolves**: one activation = one drop). A recipe's `output` is a single item name **or an `{ item: qty } bundle`**, and an optional **`roll: "supply"`** makes the craft also roll the **`SUPPLY_DROP_ROLL`** table once (first entry to pass its `chance` wins, one bonus max — the supply-drop random picker; unlike `RANDOM_DROPS`, its rows reference *existing* ITEMS keys and are boot-validated). See `enable_supply_beacon` for all three at once. **`RANDOM_DROPS`** is the bonus-treasure table: rows (`key`/`name`/`chance`%/`value`/`desc`) auto-register into `ITEMS` as treasure; actions flagged `drops: true` in `LOCATION_ACTIONS` (the foraging/woodcutting ones) roll it top-to-bottom on success — first pass wins, one drop max, announced in the action's feed line. **Treasure sells from the Backpack**: `POST /api/inventory/sell {item, qty|"all"}` (treasure-type only, gold = registry `value` × qty, `sellItem` transaction in db_backbone.js, rows stay at qty 0); the Materials tab shows descriptions under each item and a Sell button on treasure opening a quantity-or-all modal. **Adding an item/recipe = adding a row** — server.js validates the whole registry at boot (types, effect verbs, every name referenced by `LOCATION_ACTIONS`/`RECIPES`/`STATIC_UPGRADES`) and FATALs on any unknown reference, so typos die at startup, not at runtime. The admin panel's Items tab and `GET /api/admin/items` are a read-only view. **Crafting**: `GET /api/craft` returns recipes annotated per-player (`lvlOk`/`stationOk`/`toolOk`/`inputsOk`); `POST /api/craft {key}` consumes the inputs up front (atomically via `consumeItems`) and grants output + skill XP when the timer resolves (shared `ACTION_BUSY`).

**`magic_backbone.js` — the spell registry (pure data + magic-only helpers, no imports — same leaf convention as `item_backbone.js`).** `MAGIC_SPELLS` is keyed by an arbitrary spell key; each row: `name`, `type` (`attack`/`armor`/`heal`/`aid`/`travel` — `SPELL_TYPES`, which must also be a `MAGIC_SPELL_CATEGORIES` key since that map drives the Magic Table's tabs), `level` (minimum `players.s_magic_lvl` to cast *and* to learn), `desc`, `cost` (mana), `xp` (Magic skill XP granted on cast, win or miss), a type-shaped `effect` — `attack`: `{ accuracy, targets }`; `armor`: `{ ap }`; `heal`: `{ hp }`; `aid`: `{ hp_target }`; `travel`: `{ loc }` (a `LOCATION_NAMES` key) — and exactly one of **`starter: true`** (known from creation, re-granted on death — `STARTER_SPELLS` is derived from the flag) or a **`learn: { item: qty }` map** (ingredients consumed learning it). The **"Magic Backbone"** section at the bottom of the file holds the non-SQL helpers server.js uses: `validateMagicSpells(LOCATION_NAMES, ITEMS)` (boot-time FATAL, called beside the item-registry check — bad type/effect/loc, a learn map naming an unknown item, or a spell that's neither starter nor learnable all die at startup), `SPELL_ARMOR_BUFFS`/`spellApOf`, and the `MEDITATE_*` constants. **Learning — the Magic Table in Town**: `LOCATION_ACTIONS.town` opens with a **button row** (`{ key, button: true, label }` — a third row shape beside plain actions and recipe pointers: a pure UI button in the Actions card with no Do button or gating; `actionsFor` passes it through untouched and `/api/action/do` 400s it) that opens the **Magic Table modal** — category tabs from `MAGIC_SPELL_CATEGORIES`, every spell with its learn ingredients shown as have/need counts, and a Learn button. **`POST /api/spell/learn {key}`** requires being at Town, the spell's Magic level, and the ingredients (consumed atomically via `consumeItems`) — instant, shop-style, recorded in `player_magic`. Ingredients are ordinary registry `crafting` items gathered by magic-skill location actions (`arcane dust`@cave, `spirit bloom`@swamp, `ley crystal`@river, plus `mana shard`/`glowcap`). **`GET /api/spells`** returns `{ categories, spells }` with per-player annotations (`learned`, `lvlOk`, `learn` as `[{item, need, have}]`) — one payload feeding the Magic Table, the Spells cast modal (**learned spells only**), and the Player Info modal's **Skills / Spells tab pair** (Spells lists what you've learned, read-only; playercard.html's main panel likewise gained a fourth **Spells** tab from the auth-gated `spells` array in `/api/playercard`). **`POST /api/spell/cast {key}`** refuses unlearned spells (`knowsSpell`), then checks Magic level and mana cost (all before spending either), then resolves by type: `attack` rolls `effect.accuracy` against the horde and — on a hit — kills `min(effect.targets, horde_size)` through the same `resolveKill()` helper the shoot handler uses (a miss still costs the mana/XP); `armor` sets a temporary `+effect.ap` in the in-memory `SPELL_ARMOR_BUFFS` map (5 minutes, restart clears it) that `armorApOf()` adds on top of equipped-armor AP for the tick's hit calc and Base AP pooling; `heal` restores `effect.hp` via `healPlayer`; `aid` heals `effect.hp_target` to the caster or, with an optional `{target: username}`, another player (target resolved *before* the spend so a typo costs nothing; the game page UI currently always self-casts); `travel` warps straight to `effect.loc`, bypassing the travel graph. **`players.mana`/`mana_max`** are the spendable/capacity pair (`addMana` in db_backbone.js, clamped, signed-amount convention; both in `EDITABLE_STATS`); the `mana` `EFFECT_VERB` lets items restore it (Mana Potion). The Mana bar (purple, `.bg-mana`) sits between Shield and XP on the game HUD, playercard header, and admin Player Card, in playercard's always-visible bucket. The game page's **Spells** button (Loadout card) opens the cast modal, disabled when Magic level or mana falls short.

**Weapon wheel — guns plus five independent, simultaneously-equipped combat slots.** Beyond `players.equipped_gun` (guns stay in the Backpack's Guns tab, unrelated to the wheel), five more columns hold one item name each — `equipped_melee`, `equipped_fist_weapon`, `equipped_ranged`, `equipped_throwing`, `equipped_zombie_weapon` — all independently equippable at once (a player can carry a Melee weapon *and* a Fist weapon *and* a Zombie weapon simultaneously; equipping into one slot never evicts another). `players.selected_equip_slot` (`"gun"|"melee"|"fist"|"ranged"|"throwing"|"zombie"`) is server-persisted state for which slot is *active* for combat right now — survives reloads and stays in sync across tabs, unlike a client-only toggle; `POST /api/weapon/select {slot}` is the quick-swap (switch active slot without touching what's equipped), `POST /api/weapon/equip {slot, item}` equips/clears a slot (and also makes it active). `item_backbone.js`'s `WEAPONS` (every `ITEMS` row with `type: "weapon"`) carries `section` (`Melee`/`Ranged`/`Throwing`/`Fist` — the slot discriminator) and an `attack: { dmg, acc_model, targets_max? }` block; zombie-themed items (key prefix `"zombie "`, eligible for the zombie slot regardless of natural section) additionally carry `class` — their *underlying* combat style, used for reach purposes (see Zombie Location Pool below) since a Zombie Sword's `section` is `"Zombie"` but it still swings like a Melee weapon. Condition lives in `melee_condition`/`fist_weapon_condition`/`ranged_condition`/`throwing_condition` (the zombie slot has none — always reported pristine, nothing wears it); ammo is `ranged_ammo` (capped by whichever of `ranged_crossbow_max_ammo`/`ranged_bow_max_ammo`/`ranged_slingshot_max_ammo` matches the equipped ranged item's `rangedType`, plus `ranged_cb_jammed` — only crossbows jam) and `throwing_ammo`/`throwing_max_ammo`. `POST /api/action/attack {slot}` is the fully separate sibling of `POST /api/action/shoot` (guns) — same ammo/wear/jam/hit-roll shape, driven by `computeWeaponHitChance`/`weaponTargetsHit` in `server.js` against `WEAPON_ATTACK_EXPORT`'s per-section floor (`item_backbone.js`; also covers `"Zombie"`/`"Firearm"` entries for the reach-check math below) and a **Fighting skill** accuracy curve (`fightingAccuracyOf`, 40% at level 1 → 95% plateau at level 30+) parallel to how `player.accuracy` drives guns. The game page renders this as 6 slot buttons (Gun/Melee/Fist/Ranged/Throwing/Zombie, filled when active) each paired with a small quick-swap button showing what's equipped there, dynamic stat boxes that switch per active slot, and one action button whose label (Shoot/Attack/Fire/Throw) and target follow the active slot.

**Quests (`quest_backbone.js` — pure data, no imports).** `QUESTS` is keyed by an arbitrary quest key; each row: `name`, `desc`, optional `long_desc` (used by the fuller playercard view), optional `quest_level` (minimum `players.level` to *start*, not just track), `reward: { gold?, xp?, grant_instant_level? }`, a `starter` trigger (`{ starter: true }` — granted at character creation, same convention as `magic_backbone.js`'s `STARTER_SPELLS`/`STARTER_QUESTS`; `{ enter_location }`; `{ quest }` — chains off completing another quest; or `{ type: "action", action }`), and `objectives: [{ type, qty, item?|action?|recipe?|spell? }]` (`QUEST_OBJECTIVE_TYPES`: `learn_spell`/`acquire_item`/`use_item`/`action`/`recipe`/`break_horde`/`clear_raid`). Only **one quest's progress is tracked at a time** — `players.quest_active` (`'NONE'` or a key) + `quest_objectives` (JSON progress for the active quest only) + `quest_started`/`quest_completed` (comma-joined key lists). `checkQuestTriggers(userId, trigger)` (`db_backbone.js`) starts every not-yet-started quest whose starter matches (called on location entry, action success, and quest completion — chains resolve in one call); `recordQuestProgress(userId, type, matchKey, amount)` bumps the active quest's matching objective and auto-calls `completeActiveQuestIfDone`, which pays the reward, advances `quest_active` to the next started-but-incomplete quest (if any — so a queue of already-satisfied quests cascades through in one call), and fires a private `"Quest complete: <name>!"` event. `setActiveQuest`/`POST /api/quest/activate {key}` lets a player switch which started quest is tracked — objective progress is **always freshly re-seeded on activation**, not restored from an earlier stint as active (only the active quest's `quest_objectives` blob persists under this schema). `questsPayloadFor`/`questsPayloadForCard` (`server.js`) shape this into `{ active, started, completed }` for `GET /api/game-state` (game page's Quest Info card) and the richer `GET /api/playercard` variant (playercard.html's dedicated **Quests tab** — a 1-1-3 height-ratio layout: active quest, started-quest list, completed-quest accordion with full `long_desc`/`quest_level`/objective detail, vs. the game page's leaner name+reward-only completed list).

**Zombie Location Pool — three-tier zombie pools replacing the old single global counter.** Historically the whole game had one zombie count (`game_state.horde_size`) and every kill was an instant, HP-less kill. That's now the **World** tier only; two more tiers sit underneath it: **Location** (`game_state.zombies_<loc>`, one column per `ZOMBIE_LOCATIONS` entry — `location_backbone.js`) and **Nearby** (`players.zombie_near`/`zombie_near_health`, a personal per-player pool with real HP-based combat). `players.target_scope` (`"World"|"Location"|"Nearby"`, default `"World"`) picks which pool a player is fighting; `POST /api/target/select {scope}` switches it, gated (409) to only a scope that currently has zombies in it (`hasZombiesInScope`). Zombies flow between the tiers automatically in the tick (`startZombieTicker`, `server.js`): once World reaches `zombie_config.z_wander`, every `ZOMBIE_LOCATIONS` location with a player present pulls 1 zombie out of World per tick (**splintering**); below `z_wander`, 1 flows back per tick from whichever location pool is currently largest (**flow-back** — symmetric on the same threshold). While `hordeStatusOf()` reads `"hunting"`/`"raiding"`, each present player also rolls `zombie_config.z_wander_chance`% per tick for 1 zombie to move from their location's pool into their own `zombie_near` (**wander** — refills `zombie_near_health` to `zombie_config.z_hp`; deliberately distinct internal naming from `hordeStatusOf()`'s unrelated `"wandering"` status tier, which they happen to share a word with). **"Zombie force"** (`zombieForceOf`) is what actually attacks a player each tick: their targeted pool's count *plus* `zombie_near` (never just the latter alone unless Nearby *is* the targeted scope, to avoid double-counting) — a player's own Nearby pool always threatens them regardless of what they're targeting. The **raid mechanic is completely untouched** by any of this — it still samples from the global `horde_size` only; per-player force replaces the old shared tick-wide roll solely for the non-raid wandering/hunting tiers, so hunting now feels different player-to-player based on individual exposure. **Two resolution paths**: World/Location kills stay the old instant-kill "Broad" flow (`resolveKill`, now scope-aware — decrements the right pool, and the horde-broken/raid-cleared token bonus only ever evaluates for World-scope kills); Nearby is real HP combat against `zombie_near_health` via `damageNearbyZombie` — a swing applies its weapon's `dmg` (guns: `WEAPON_FIREARM_EXPORT` in `item_backbone.js` — the single accuracy/damage/`maxTargets` model shared by both World/Location and Nearby-scope gun combat; weapon-wheel items: their own inline `attack` block) and, on a kill, refills health for the next queued zombie and — if under the swing's `targets_max` and the pool isn't empty — cascades into it with the same swing (Golden Gun instant-kills the queued zombie the same way it instant-kills in Broad mode). **Attack-reach gate**: Melee/Fist/Throwing weapons (resolved through a zombie-themed item's `class` when its `section` is `"Zombie"`, else its `section` directly — `weaponReachOf`) can only be used while `target_scope === "Nearby"` — "too far away," 409 otherwise; Ranged and guns work at any scope. **Travel** (`POST /api/travel`) 409s above `zombie_near > 3`; a successful travel flushes whatever's left (0-3) into the *departing* location's pool and zeroes the player's Nearby pool — zombies are conserved, never deleted or teleported. The Hunt Info card's old "Horde" box is now a sectioned **"Targeted Zombies"** box: World/Location/Nearby counts each with a Target/Selected toggle, a **Main** number (the currently-targeted pool's raw count), and a **"Targeting You:"** pill (the zombie-force value) — Raid/Hunt boxes are untouched. The map modal shows a zombie-count badge per `ZOMBIE_LOCATIONS` entry (none on safe locations).

**Zombie Outbreak mode — a world event layered on top of the Zombie Location Pool, now fully wired end to end (backend mechanics + player-facing UI + admin controls).** `game_state.total_z_pool` is the true zombie count *everywhere* (World + all 8 `zombies_<loc>` columns + every player's `zombie_near`) — distinct from `horde_size`, which is World-only. It's kept in sync structurally rather than by hand: `adjustHordeSize`/`adjustLocationZombies`/`adjustZombieNear`/`setLocationZombies` (`db_backbone.js`) each mirror their own post-clamp delta into it, so any balanced transfer between two pools (splinter, flow-back, wander, travel-flush) nets to zero automatically, and only real spawns/kills/admin overrides show up as a net change — `damageNearbyZombie`'s kill branch and `updatePlayerLocation`'s travel-flush are the two spots that needed an explicit assist since they write around the mirrored primitives directly. Every tick (`startZombieTicker`, `server.js`), once `total_z_pool >= zombie_config.z_break` an in-memory tic counter climbs toward `z_break_tic_run`; once there, `z_break_players`-online and `z_break_interval`-since-last-outbreak gates are checked and a `z_break_chance`% roll is attempted (`triggerOutbreak()`). A trigger consolidates `total_z_pool` and splits it evenly across the 8 `OUTBREAK_LOCATIONS` (remainder to Forest), zeroes `horde_size`, sweeps every player's `zombie_near` into the split, and sets `game_state.zombie_break = 1` — from that moment the tick's normal spawn/splinter/wander/tiered-attack all stop, replaced by a single "hive-mind" `z_hit`%-per-tick roll that, on a hit, damages *every* present player at *any* `OUTBREAK_LOCATIONS` location with zombies (through the same `applyZombieHitToPlayer` shield/AP-block/Defense-XP/armor-degrade pipeline the normal tick uses — factored out specifically so both share it). Players can still fight back with ordinary Location-scope combat, which decrements `total_z_pool` like any other kill. Two ways it ends: **early** — `total_z_pool` drops to `z_break - z_break*(z_break_fall%)` (a fixed target off the static config number, not the actual triggered total) — flows every `OUTBREAK_LOCATIONS` pool back into `horde_size`, clears the flag, and pays `zombie_config.z_break_reward` to every online player via the shared `applyReward()`; **late** — `zombie_config.z_break_duration` elapses first ("zombies win"): every online player standing somewhere with zombies dies (full reset), `game_state.z_break_defeated_at` is set, and the world freezes on that timer (mirroring `base_destroyed_at`'s pattern) for `zombie_config.z_break_reset` hours before an Experiment Reset — which now also zeroes `total_z_pool`/every `zombies_<loc>`/`zombie_break`/`z_break_falltime`/`z_break_defeated_at` (a pre-existing gap in `resetGameState()` that predated Outbreak mode but was load-bearing for it). `applyReward(userId, reward)` (`db_backbone.js`) is the shared `{gold, tokens, xp, items, level}` handler behind both `z_break_reward` and quest completion — `level: N` (free instant levels via `forceLevel`) takes priority over the older boolean `grant_instant_level` if a reward carries both, so the two are never read as stacking. **Player-facing wiring**: a single shared `isZombieActive(location, gs)` helper (`server.js`, beside `locationZombiesOf`) — true for the always-active `ZOMBIE_LOCATIONS`, plus any `OUTBREAK_LOCATIONS` member while `zombie_break === 1` — is now what every location-danger check reads (game.html's `zombieZone`/map badges, the shoot/attack/call-zombie/spell-cast 409s, meditate's inverted safe-zone check, the admin panel's display flags); game.html's Hunt-Info↔Actions and Loadout↔Adventure-Panel swap was already single-flag-driven, so this was the whole client-side fix. `GET /api/game-state` also exposes a top-level `outbreak` boolean now, driving a pulsing "!!! Zombie Outbreak Active !!!" banner (`#outbreakBanner`) that replaces the header's Hunt/Horde/Zombies pills while active, and disabling the hunt-toggle/vote-start buttons — **the hunt cannot be toggled or vote-started by anyone while an Outbreak is active** (`/api/hunt/toggle` and `/api/hunt/vote/start` both 409; `triggerOutbreak()` also `cancelHuntVote()`s anything mid-flight), so admins can't end an Outbreak by simply turning the hunt off. The web admin panel's World tab Horde box swaps to a `!!OUTBREAK!!` view while active (Total Zombie Force = `total_z_pool`, a **Force End** button) in place of the normal horde controls; Force End (`POST /api/admin/world/outbreak/forceend`) zeros every `OUTBREAK_LOCATIONS` location except Forest (set to `z_break - 5`, floored at 0) and clears `zombie_break` immediately with no freeze/reset and no reward — a clean admin override distinct from both natural end paths.

**`util/` — Admin CLI.** `index.mjs` runs a single command and exits when given argv (what the `menus/*.sh` dialogs call), else a readline REPL. `parser.mjs` routes `<group> <action> <args...>` to `commands/{users,players,inventory,database}.mjs`; `help` lists the groups and `help <group>` prints that group's commands with usage (backed by a `HELP` table in `parser.mjs` — update it when adding commands). Notable: `players stats|statsraw|getstat|setstat|forcelevel|guns|setgun` (the interactive editors in `menus/players.sh` — a stat menu with ±1/5/10/set, `level` special-cased to a full-stack `forcelevel` control, and a gun-equip menu with `setgun … force` — are built on the `*raw`/`guns`/`getstat` outputs), `users list|names|add|setpassword|setadmin|remove` (the `menus/users.sh` "List Users" opens a picker → per-user manage submenu), and the **`database` group** (`backup`/`backups`/`restore`/`check`/`update`/`migrate`/`inspect`, see toolkit below). `menus/lib.sh` provides the shared `pick_user` "Enter name/list" picker.

**Database toolkit** (`util/commands/database.mjs`, driven by `menus/database.sh`): **never imports `db_backbone.js`** — it resolves the live DB path from `config.js` (honoring the `DB_PATH` env override, same as db_backbone.js) and builds its **reference schema** by letting `db_backbone.js` create a pristine temp DB in a child process (`DB_PATH` overridden), so it self-updates as the schema evolves *and* still works when the live DB is outdated. `util/parser.mjs` lazy-loads the command groups for the same reason: only the invoked group's module (and thus `db_backbone.js`, for users/players/inventory) is ever imported. `backup` writes a timestamped `backup_database_<YYYYMMDD-HHMMSS>.bak` under **`util/backups/`** (gitignored, so wiping `data/` never touches them); `restore` picks from the list and copies over the live DB (clears stale WAL/SHM); `check` compares the live DB against a fresh schema (multi-line report; the menu branches on its first word — OK/OUTDATED/MISSING/INVALID) and `update` adds whatever's missing in place — together they're the menu's "Check For Schema Updates"; `migrate <path>` does the same for an arbitrary old DB file (creates missing tables, adds missing columns with correct defaults) or reports it invalid — the menu's "Migrate Old Database" prompts you to drop old DBs into **`data/import/`**, then offers the files found there (with sizes) as a picker. Backups use `better-sqlite3`'s online `.backup()` (safe while running); restore/update/migrate of the live DB assume the server is stopped (the menu enforces it for restore and schema update).

**Logging.** `log(level, message, config, fileMessage?)` in `server.js`. Levels ascending: `FULL`(0, plumbing) < `API`(1, per-request session/auth/crypto tracing) < `INFO`(2, actions + tick results) < `WARN` < `ERROR` < `FATAL`. Console output requires `--verbose` and is colorized per level via `util.styleText` (auto-no-ops when the stream can't color; the log file stays plain). File writes happen in dev mode or for ERROR/FATAL. `FATAL` exits. **`API` is a hard special case, not just another verbosity rung**: `log()` branches on it before anything else — it never reaches the console and never writes to `logs/server.log`, regardless of `--verbose`/`--debug-level`; dev-mode-gated like everything else, it writes exclusively to `logs/<logFile>.api` (`LOG_FILE_API`). It exists so the chatty per-request tracing that used to flood the main log on every 3s game-state poll (`requireAuth`/`getSession`/`sign`/`hashPassword`'s session-check and crypto lines, the generic "page served" lines) has somewhere to go that clutters neither the console nor the file people actually grep for game events. **`login`/`register`'s own narrative lines are deliberately *not* reclassified** — attempt/blocked-reason/success stay at their original `FULL`/`WARN`/`INFO`/`ERROR` levels, so they're the one per-auth-request thread that still shows up in console + the main log. **In dev mode, the console filter defaults to INFO** unless a level was explicitly set (`NONE` is the config default sentinel). A startup summary (mode/debug/tick/timeout) is always printed and logged, ungated; `timeout > 10` prints an "excessive" warning. **Sensitive-value redaction:** the optional 4th `fileMessage` arg is the version written to the log file — the console still shows the raw `message`, but the file gets the redacted one. Password/session lines (salts, the signed session cookie, payloads) pass `"…[redacted]"` for the file so nothing usable ever lands in either log file. **Rotation:** `logs/server.log` and `logs/server.log.api` are capped independently at `file_config.logMaxMB` (3MB) each; at the cap a file rotates to its own `.old` file (replacing the previous rotation) with a `--verbose` console warning — `rotateLogIfNeeded(file, rotated)` takes the target explicitly (defaulting to the main log) and is checked before every `log()` file write of that target (the few direct `appendFileSync` writers against the main log rely on the startup check only). `menus/logs.sh` can view the rotated file. **`db_backbone.js` gets write access to this facility too, despite owning no logging of its own** — it has no `log`-related import (importing `server.js` back would be circular) and its own `insertEvent()` only ever writes to the in-game `events` feed, not a log file. `server.js` calls the exported `setLogger()` once at boot with a small closure over `log`/`game_config`, letting the handful of real game-rule decisions that live there (quest start/activation/completion + reward payout in `startQuest`/`activateQuest`/`completeActiveQuestIfDone`/`applyReward`, Nearby-zombie swing resolution in `damageNearbyZombie`) log precisely at the point of decision.

## Conventions & gotchas

- **Config is five objects in `config.js`:** `file_config` (log/db/censor filenames, `logMaxMB`), `ssl_config` (`enabled`, `certFile`/`keyFile` — see HTTPS below), `game_config` (verbose, dev, debugLevel, `sessionSecret`, timeout, heartbeatSeconds, baseMaxHealth, experimentResetHours, tokenExchangeGold), `zombie_config` (z_tic, z_chance, z_hit, z_damage, z_horde, z_raid, z_wander, z_wander_chance, plus the Outbreak-mode group `z_break`/`z_break_players`/`z_break_interval`/`z_break_tic_run`/`z_break_chance`/`z_break_duration`/`z_break_reward`/`z_break_fall`/`z_break_reset` — see Zombie Outbreak mode above), `account_config` (`ban_timeout` — default temp-ban length in seconds when a ban omits one; `failed_login_max`/`failed_login_lockout_seconds` — the automatic lockout, see moderation below). `sessionSecret` defaults to `'changeme'` and **must** be overridden for real deployments. Env overrides: `DB_PATH`, `PORT` (the old `HUNT_TICK_MINUTES` is gone). **`config.js` also exports `app_version` — the single source of truth for the version string** (startup summary + `--help` read it); only `changelog.md` and `README.md` state their own versions, and `package.json` deliberately has no `version` field.
- **Dev DB = delete & rebuild, no migrations.** This is a strictly dev build; when the schema changes, delete `data/zboe.sqlite*` and let `db_backbone.js` recreate it. Don't add `ALTER TABLE` migrations — real "old DB" migration is deferred to a future zboe2→zboe3 push. The two existing `ALTER`s (location/hidden) are legacy leftovers.
- `.gitignore` excludes `data/`, `logs/`, `util/`, `zboe.sh`, the install scripts, `package-lock.json`, `.env*`, and `*.sqlite`/`*.log` — so the Admin CLI (`util/`) is untracked, but `menus/` and `CLAUDE.md` are **tracked**. DB backups live under `util/backups/` on purpose (gitignored + survives wiping `data/`). Don't assume the working tree matches the repo.
- `scratchbook.js` / `scratchbook.note` are ignored scratch space, not part of the app.
- **`horde_size` (in `game_state`) is the single source of truth for the zombie count.** `horde_status` (`hiding`/`wandering`/`hunting`/`raiding`) comes from `hordeStatusOf()`, which reads the `raid_enabled` **latch** first (raid persists once triggered until the horde hits 0) then derives wandering/hunting from `z_horde`. `spawn`/`kill` events are narrative feed flavor, not counters.
- **Web admin & CLI share game logic via `db_backbone.js`.** `EDITABLE_STATS`/`setPlayerStat` (whitelisted, clamped stat writes) and the leveling rules are defined once in `db_backbone.js` and used by both `util/commands/players.mjs` and the `/api/admin/*` panel — change them there, not in two places.
- **Player location lives on `players.location`** (default `basecamp_outside`) — no `locations` table. The world is defined in `location_backbone.js`: `LOCATION_NAMES` (key → display name) and `LOCATION_LINKS` (the travel graph — Bunker hangs off Basecamp only; Forest is the hub to lake/mountains/river/swamp/cave/town). `POST /api/travel {to}` validates adjacency (plus, since the Zombie Location Pool work, a 409 if `players.zombie_near > 3` — see below); `locationOf()` in `server.js` hardens unknown/NULL values to Basecamp. **`ZOMBIE_LOCATIONS` (location_backbone.js) gates all zombie contact**: basecamp (outside *and* inside — the base siege still works), forest, lake, swamp. Everywhere else is safe — the tick filters those players out entirely, and shoot/call-zombie 409 ("It's quiet here"). In safe zones the game page swaps the Hunt Info card to **"Actions"** (hunt stats hidden, location box stays) and disables Shoot/Call Zombie — and the Loadout card becomes the **Adventure Panel**: same HUD + Player Info, but gun stats/combat buttons swap for **Build Campfire** (consumes 2 firewood, burns 5 min — `CAMPFIRES` map in server.js, in-memory like `ACTION_BUSY`), **Cook Food** (modal of campfire-station recipes, enabled only while burning), **Put Out Fire**, and **Meditate on Magical Theory** (`POST /api/meditate` — safe zones only, 20s busy, +8 Magic XP). At the Mountains the Adventure Panel adds the **forge controls**: a fired-status pill, **Use Forge** (modal of forge-station recipes, enabled only while `me.forgeFired` — split into **Smelting/Smithing main tabs** (derived from the recipe key: `smelt_*` → Smelting) with **section headers** inside each, driven by the recipes' registry `section` field (Ingredients/Tools/Iron/Silver/Gold/Mythril/Adamantite/Syllic — required on forge recipes, boot-validated)), and **Put Out Forge** (`POST /api/forge/toggle` — off only; lighting goes through the skill-gated `fire_forge` action, which consumes a firewood). The **map modal lists only reachable locations**, each with a color-coded safe/zombies pill, and shows a base-HP pill when away from Basecamp (since the Base card is hidden there). `basecamp_inside` is the base interior — entered only via `/api/base/toggle` (which requires being at Basecamp), never via the map; while inside, the map is hidden and travel is refused. The game page's Map button (location box) opens a modal listing every location with Travel buttons on reachable ones; the Base card (health bar + toggle) renders only while `me.atBase`. `getLocationCount()` in `db_backbone.js` is still unreferenced — reserved for per-location occupancy/actions.
- **Backgrounding:** without `--verbose` the server daemonizes (self-respawn detached, writes `logs/zboe.pid`); `--stop` kills it. Only one backgrounded instance is tracked (single PID file), and a live PID file blocks a second background start. `menus/server.sh` drives this.
- **`sessionSecret` sanity halt:** while it's the default `'changeme'`, non-dev runs FATAL-exit at startup and dev runs only warn — set it before any real run.
- Several dead/duplicate `log(...)` calls sit after `return` in some route handlers (they never execute); don't treat them as reachable behavior.
- **`server.js` is internally split into two top-level banner sections: `Helpers` then `Server`.** Helpers holds every reusable function/const with no execution-order dependency on anything below it (combat math, auth/session middleware functions, the quest/horde/hunt-vote/weapon-wheel/location-action helpers, the chat censor, `STATIC_UPGRADES`/`EFFECT_VERBS`, kill resolution — none of it references anything declared later in the file). Server holds the CLI/daemon boot sequence, Express app + middleware registration, boot-time registry validation, every route (grouped by feature), the zombie tick, and the final startup bootstrap (`server.listen()` is always the last statement). When adding a new small reusable helper, put it in the Helpers section, not inline near its first caller — `const`-declared values (unlike `function` declarations, which hoist) must be declared before anything that runs at module-load time references them, and Helpers-first is the standing convention that avoids ever having to think about it.
